## 0.2 프로젝트의 핵심 정체성

Xdaptive는 사용자 의도를 중심으로 소프트웨어를 생성하고, 구성하고, 실행하며, 변화시키는 새로운 컴퓨팅 운영체제를 개발하는 오픈소스 프로젝트다.

Xdaptive가 추구하는 것은 기존 운영체제에 AI 기능을 추가하는 것이 아니다.

소프트웨어의 구성과 실행, 변경 및 생명주기를 운영체제 차원에서 관리함으로써 기존의 프로그램 중심 컴퓨팅 모델을 넘어서는 것이다.

기존 컴퓨팅 환경에서는 사용자가 이미 만들어진 프로그램을 선택하고, 프로그램의 기능과 인터페이스에 자신의 작업을 맞춰야 한다.

Xdaptive는 이 관계를 반대로 바꾸고자 한다.

사용자가 수행하려는 작업을 중심으로 운영체제가 필요한 소프트웨어 환경을 구성하고, 작업이 변화하면 소프트웨어도 기존 상태를 유지하면서 적응하도록 한다.

**Beyond Applications.**

애플리케이션이라는 고정된 소프트웨어 경계를 넘어, 사용자의 의도와 작업에 맞춰 구성되고 변화하는 컴퓨팅 환경을 지향한다.

## 0.3 핵심 철학

> **Adaptation is a system capability.**

적응은 개별 애플리케이션이 제공하는 부가 기능이 아니라 시스템 자체가 가져야 할 능력이다.

Xdaptive에서 적응은 단순히 UI를 바꾸거나 기존 프로그램을 자동화하는 것이 아니다.

소프트웨어의 구성, 데이터 흐름, 실행 구조, 기능, 인터페이스 및 상태를 운영체제 차원에서 이해하고 관리하며, 필요에 따라 안전하게 변경하는 능력을 의미한다.

AI는 이러한 과정에서 사용자의 의도를 해석하고 변경 계획을 제안하는 수단 중 하나다. 그러나 Xdaptive의 본질은 AI 자체가 아니라 소프트웨어를 구성하고 실행하며 변화시키는 독자적인 시스템 구조에 있다.

## 0.4 오픈소스 개발 원칙

Xdaptive는 오픈소스 프로젝트로 발전시킨다.

단순히 완성된 소스 코드를 공개하는 것이 아니라, 프로젝트의 명세와 설계 과정, 구현 및 검증 과정을 공개적으로 발전시키는 것을 지향한다.

핵심 기술은 외부에서 검토하고 실험할 수 있는 형태로 개발한다.

다만 오픈소스라는 개발 방식이 기술적 완성도나 보안 검증을 대신하지는 않는다. 공개된 명세와 구현은 실제 테스트와 측정을 통해 검증되어야 한다.

# 1. 프로젝트 개요

## 1.1 프로젝트의 출발점

현재 컴퓨터 운영체제에서 사용자는 특정한 작업을 수행하기 위해 여러 프로그램을 직접 선택하고 조합해야 한다.

예를 들어 데이터를 분석하려면 스프레드시트 프로그램, 데이터 분석 환경, 시각화 도구 등을 각각 사용해야 한다. 영상 편집을 하려면 영상 편집기, 음성 인식 도구, 오디오 편집 프로그램 등을 별도로 실행하고 서로 연결해야 한다.

이러한 구조에서는 사용자가 작업을 수행하기 전에 먼저 적절한 소프트웨어를 찾아야 하며, 각 프로그램의 사용법과 한계를 이해해야 한다.

소프트웨어는 개발자가 미리 정의한 기능과 인터페이스를 중심으로 만들어지고, 사용자는 이미 만들어진 소프트웨어의 구조에 자신의 작업을 맞추게 된다.

AI 기술의 발전으로 자연어를 통해 프로그램을 생성하거나 기존 프로그램을 자동화하는 것이 가능해졌지만, 대부분의 접근은 기존 운영체제와 소프트웨어 모델을 유지한 채 AI를 추가하는 방식에 머물러 있다.

Xdaptive는 이 전제 자체를 다시 검토하는 데서 출발한다.

**사용자가 프로그램을 선택하는 것이 아니라, 사용자의 작업에 맞춰 소프트웨어 환경 자체가 구성되고 변화하는 운영체제를 만든다.**

## 1.2 핵심 비전

Xdaptive의 목표는 AI를 기존 운영체제에 탑재하는 것이 아니다.

운영체제가 소프트웨어의 생성, 구성, 실행, 최적화, 변경 및 생명주기를 직접 관리하는 새로운 컴퓨팅 환경을 구축하는 것이다.

사용자는 여러 프로그램을 직접 실행하고 연결하는 대신, 자신이 수행하려는 작업을 제시한다.

운영체제는 해당 의도를 해석하고 필요한 기능과 실행 구조를 구성하여 하나의 통합된 작업 환경을 제공한다.

작업이 진행되면서 새로운 요구사항이 발생하면 기존 작업 상태를 유지하면서 필요한 기능과 인터페이스를 변경한다.

따라서 소프트웨어는 더 이상 고정된 완제품이 아니라 사용자의 작업에 맞춰 구성되고 진화하는 실행 환경이 된다.

### 핵심 문장

> An operating system that generates, compiles, executes, and evolves software around human intent.

> Software is no longer fixed. It adapts to the task.

> **Beyond Applications.**

> **Software that adapts to your intent.**

> **Adaptation is a system capability.**

Xdaptive는 이러한 기술적 방향을 바탕으로 개발하는 Adaptive Computing OS다.

# 2. 기존 운영체제와의 근본적인 차이

## 2.1 기존 소프트웨어 모델

일반적인 운영체제에서 소프트웨어는 다음과 같은 구조를 가진다.

1. 개발자가 프로그램의 기능과 구조를 미리 설계한다.
2. 사용자는 프로그램을 설치한다.
3. 프로그램은 개발자가 정의한 기능과 인터페이스를 제공한다.
4. 사용자는 프로그램의 사용법을 익히고 기능을 조합한다.
5. 작업이 복잡해지면 여러 프로그램을 연결한다.

이 구조에서는 소프트웨어가 중심이고 사용자의 작업이 소프트웨어에 종속된다.

## 2.2 새로운 소프트웨어 모델

Xdaptive에서는 작업이 중심이 된다.

1. 사용자가 수행하려는 작업을 제시한다.
2. 운영체제가 작업을 분석한다.
3. 필요한 기능과 데이터 흐름을 결정한다.
4. 소프트웨어 구성 요소를 선택하거나 새롭게 생성한다.
5. 컴파일러와 런타임이 이를 검증하고 실행한다.
6. 작업의 변화에 따라 소프트웨어 환경을 수정한다.
7. 작업이 종료되거나 더 이상 필요하지 않은 기능은 정리한다.

이 구조에서는 소프트웨어가 작업에 종속된다.

| 구분 | 기존 OS | Xdaptive OS |
|---|---|---|
| 중심 개념 | 프로그램 | 작업 |
| 소프트웨어 | 고정된 완제품 | 동적으로 구성되는 실행 환경 |
| 사용자 경험 | 프로그램 중심 | 작업 중심 |
| 기능 확장 | 설치, 플러그인, 설정 | 기능 단위의 동적 구성 |
| 프로그램 간 연결 | 사용자가 직접 연결 | OS가 작업에 맞게 구성 |
| 인터페이스 | 프로그램별로 고정 | 작업에 따라 변화 |
| 작업 상태 | 프로그램별 저장 | Workspace 중심으로 통합 관리 |
| 변경 방식 | 프로그램 내부 설정과 수동 조작 | 구조적 변경 및 증분 적용 |

이 프로젝트가 추구하는 변화는 단순한 자동화가 아니라 소프트웨어가 구성되고 사용되는 방식 자체의 변화다.

# 3. 핵심 사용자 경험: 하나의 통합 프로그램

## 3.1 하나의 프로그램이라는 개념

Xdaptive의 중요한 특징은 사용자가 여러 프로그램을 직접 다룰 필요가 없다는 것이다.

다만 여기서 말하는 하나의 프로그램은 내부적으로 하나의 프로세스만 존재한다는 뜻이 아니다.

사용자에게는 하나의 통합된 인터페이스와 Workspace가 제공되지만, 내부에서는 여러 엔진, 서비스, 프로세스 및 실행 모듈이 독립적으로 동작할 수 있다.

운영체제는 이 구성 요소들을 통합적으로 관리한다.

예를 들어 데이터 분석 작업에서는 CSV 처리 엔진, 데이터 분석 모듈, 시각화 엔진이 함께 동작할 수 있다.

사용자는 각각의 프로그램을 직접 실행하거나 연결할 필요가 없다.

OS가 작업에 적합한 구성을 만들고 이를 하나의 작업 환경으로 제공한다.

## 3.2 Workspace

이 통합 환경을 **Workspace**라고 정의한다.

Workspace는 단순한 화면이나 여러 프로그램을 모아 놓은 컨테이너가 아니다.

하나의 작업을 수행하기 위한 독립적인 실행 환경이자 지속적인 상태 관리 단위다.

Workspace는 다음 요소를 포함한다.

### Identity

- 고유 ID
- 사용자 작업의 목표
- 생성 시각
- 현재 버전
- 작업 상태

### Software Configuration

- 연결된 엔진과 서비스
- 활성화된 Capability
- 각 구성 요소의 설정
- 소프트웨어 간 연결 관계

### Workflow State

- 작업 단계
- 작업 의존성
- 실행 상태
- 진행 상황
- 실패 및 재시도 정보

### Interface State

- 화면 레이아웃
- 패널 구성
- 도구 배치
- 사용자 설정
- 인터페이스 버전

### Data State

- 입력 데이터
- 중간 결과
- 최종 결과
- 데이터 참조 및 변경 기록

### Version History

- Workspace 변경 이력
- 복구 지점
- 구성 변경 기록
- 실행 상태의 체크포인트

Workspace는 작업이 진행되는 동안 계속 진화한다.

사용자가 새로운 기능을 요청하면 기존 작업 환경을 폐기하고 처음부터 만드는 것이 아니라, 기존 상태를 보존하면서 필요한 부분을 변경한다.

## 3.3 Workspace의 독립적인 생명주기

Workspace는 운영체제가 관리하는 독립적인 객체로 취급한다.

기본 생명주기는 다음과 같다.

1. Create: 작업 환경 생성
2. Initialize: 필요한 기능과 엔진 구성
3. Execute: 작업 실행
4. Extend: 기능 추가
5. Adapt: 구조 및 인터페이스 변경
6. Persist: 상태 저장
7. Restore: 이전 상태 복구
8. Clone: 작업 환경 복제
9. Terminate: 작업 환경 종료

Workspace의 상태와 실제 실행 중인 프로세스의 메모리 상태는 구분해야 한다.

설정과 작업 명세를 저장했다고 해서 모든 프로세스의 실행 상태가 자동으로 복구되는 것은 아니다.

따라서 엔진별 체크포인트, 실행 로그, 재실행 가능한 작업 명세 등을 함께 관리해야 한다.

또한 Software Configuration, Workflow, Interface, Data의 버전을 구분한다.

UI를 변경했다고 해서 데이터 상태까지 불필요하게 새로운 버전으로 취급할 필요는 없기 때문이다.

# 4. 소프트웨어의 동적 구성과 적응

## 4.1 Adaptive Software

Xdaptive의 핵심 개념은 **Adaptive Software**다.

기존 프로그램의 기능과 구조를 작업에 맞게 재구성하고, 필요한 경우 새로운 기능을 생성하여 결합하는 접근이다.

기존 프로그램을 무조건 수정하거나 전체를 재작성하는 방식은 아니다.

소프트웨어마다 가능한 변경 범위가 다르기 때문이다.

이를 세 가지 단계로 구분한다.

### Level 1. Interface Adaptation

사용자 인터페이스를 작업에 맞게 변경한다.

- 패널 배치 변경
- 불필요한 UI 요소 제거
- 필요한 도구 표시
- 작업에 적합한 컨트롤 생성
- 여러 기능을 하나의 인터페이스로 통합

### Level 2. Workflow Adaptation

기존 기능을 연결하고 실행 흐름을 변경한다.

- 기능 간 데이터 전달
- 실행 순서 변경
- 여러 엔진 연결
- 작업 단계 자동화
- 조건부 실행 및 결과 처리

### Level 3. Program Adaptation

프로그램의 동작과 기능 자체를 변경하거나 확장한다.

- 새로운 기능 생성
- 기존 기능의 동작 변경
- 내부 모듈 재구성
- 호환 가능한 기능 재구현
- 실행 구조 및 데이터 처리 방식 최적화

모든 소프트웨어가 Level 3까지 지원되는 것은 아니다.

운영체제는 각 소프트웨어가 지원하는 변경 범위를 파악하고, 가능한 범위에서 적응을 수행해야 한다.

## 4.2 소프트웨어 접근 방식

소프트웨어의 종류에 따라 서로 다른 적응 전략을 적용한다.

| 소프트웨어 유형 | 접근 방식 |
|---|---|
| 자체 개발 소프트웨어 | 내부 구조 및 Extension API를 이용한 직접 재구성 |
| 오픈소스 소프트웨어 | 플러그인, API, 소스 수정, 모듈 재구성 |
| 외부 독점 소프트웨어 | 공식 API, IPC, 접근성 인터페이스, 자동화 |
| 분석 가능한 바이너리 | 리버스 엔지니어링 및 동작 분석 |
| 지원이 제한된 소프트웨어 | 외부 프로그램 또는 독립 서비스로 연결 |

핵심은 모든 프로그램을 동일한 방식으로 다루지 않는 것이다.

운영체제는 각 소프트웨어의 구조와 기능을 이해하고 적절한 방법으로 활용해야 한다.

# 5. 리버스 엔지니어링의 역할

## 5.1 리버스 엔지니어링을 활용하는 이유

기존 설계에서는 외부 소프트웨어의 공식 API나 Extension 기능에 의존하는 비중이 높았다.

그러나 이러한 접근만으로는 활용할 수 있는 기능이 제한된다.

리버스 엔지니어링 기술을 적극적으로 활용하면 공개된 소스 코드가 없는 소프트웨어도 내부 구조와 동작을 분석하고, 기능을 이해하거나 호환 구현을 시도할 수 있다.

이는 Xdaptive의 소프트웨어 이해 능력을 확장할 수 있는 중요한 기술적 방향이다.

다만 리버스 엔지니어링은 모든 소프트웨어를 자동으로 오픈소스화하는 기술이 아니다.

바이너리 분석, 동작 이해, 소스 코드 복원, 호환 구현, 재배포 권한은 서로 다른 문제다.

기술적으로 분석할 수 있다는 사실이 원본 코드의 복제나 재배포를 허용한다는 의미도 아니다.

## 5.2 Software Understanding & Reconstruction

리버스 엔지니어링을 활용하는 독립적인 기술 계층을 구상한다.

### 1. Software Analyzer

소프트웨어의 구조와 동작을 분석한다.

- 바이너리 분석
- 함수 및 제어 흐름 분석
- 데이터 구조 추론
- UI 및 사용자 상호작용 분석
- IPC 및 네트워크 동작 분석
- 의존성 분석

### 2. Semantic Reconstruction

분석 결과를 OS가 이해할 수 있는 의미적 모델로 변환한다.

- 기능의 목적
- 입력과 출력
- 데이터 구조
- 기능 간 의존성
- 실행 조건
- 상태 변화
- 외부 인터페이스

### 3. Adaptation Generator

분석된 기능을 활용할 수 있는 형태로 만든다.

- 기존 기능 연결
- 호환 구현 생성
- 필요한 기능의 독립적 구현
- 인터페이스 및 Workflow 구성
- 기능별 검증

### 4. Adaptive Composition Engine

검증된 기능들을 작업에 맞게 결합하여 Workspace를 구성한다.

## 5.3 리버스 엔지니어링의 한계

다음 문제를 고려해야 한다.

- 최적화된 바이너리에서는 원래의 소스 구조가 손실될 수 있다.
- 난독화 및 암호화된 프로그램은 분석이 어려울 수 있다.
- 서버 측 로직은 클라이언트 분석만으로 파악할 수 없다.
- 대규모 프로그램 전체를 분석하는 데는 많은 시간과 자원이 필요하다.
- 분석 결과가 잘못되면 기능을 잘못 이해하거나 잘못 재구현할 수 있다.
- 라이선스 및 적용 법률에 따라 분석과 재구현의 허용 범위가 달라질 수 있다.

따라서 리버스 엔지니어링은 모든 소프트웨어를 무조건 변형하기 위한 만능 수단이 아니라, OS의 소프트웨어 이해 능력을 확장하는 하나의 핵심 기술로 취급한다.

# 6. 프로젝트의 독자적인 기술

Xdaptive는 기존 AI 모델이나 외부 소프트웨어를 단순히 연결하는 데 그치지 않는다.

독자적인 기술의 중심은 소프트웨어를 표현하고, 분석하고, 실행하며, 지속적으로 변경하는 자체 컴퓨팅 모델을 만드는 것이다.

특히 다음 네 가지 기술을 핵심 연구 대상으로 설정한다.

## 6.1 Adaptive IR (AIR)

**Adaptive Intermediate Representation**

Adaptive IR은 운영체제가 소프트웨어의 구성과 변경을 표현하기 위한 중간 표현이다.

AI가 생성한 자연어 기반 계획이나 소프트웨어 분석 결과를 직접 실행해서는 안 된다.

대신 이를 구조화된 IR로 변환하고 검증한 후 실행한다.

AIR은 다음 내용을 표현할 수 있도록 설계한다.

- 소프트웨어 구성 요소
- Capability 활성화 및 비활성화
- 기능 간 연결 관계
- 데이터 흐름
- Workflow
- UI 구성
- 상태 보존 및 이전
- 권한과 실행 조건
- 리소스 요구사항

AIR은 단순한 설정 파일이 아니라 OS의 구성 및 실행 모델과 연결되는 핵심 기술이다.

다만 초기부터 모든 종류의 소프트웨어를 표현하려고 지나치게 복잡한 DSL을 만드는 것은 피한다.

실제 MVP에 필요한 최소한의 표현부터 설계하고 점진적으로 확장한다.

## 6.2 Adaptive Compiler

Adaptive IR을 실제 실행 가능한 구조로 변환하고 최적화하는 자체 컴파일러다.

컴파일러는 단순히 코드를 생성하는 도구가 아니다.

운영체제가 관리하는 소프트웨어 구성과 실행 계획을 분석하고, 안전하고 효율적인 실행 구조로 변환하는 역할을 맡는다.

주요 기능은 다음과 같다.

- AIR Parser
- AST 구성
- 정적 타입 검사
- 의미 분석
- Typed IR 생성
- 의존성 분석
- 데이터 흐름 분석
- 실행 계획 최적화
- 증분 컴파일
- 코드 및 실행 모듈 생성
- 검증된 실행 계획 전달

AI가 프로그램을 생성하더라도 실제 실행을 책임지는 것은 Adaptive Compiler다.

따라서 AI의 생성 결과와 OS가 보장하는 실행 결과를 분리할 수 있다.

일반적인 작업은 AI의 개입 없이 네이티브 실행이 가능해야 한다.

## 6.3 Adaptive Execution Architecture

프로그램을 고정된 실행 파일이 아니라 동적으로 구성하고 변경할 수 있는 실행 단위로 취급하는 자체 실행 모델이다.

기존 프로그램을 무조건 새로 생성하는 것이 아니라, 기존 실행 상태와 기능을 최대한 보존하면서 필요한 부분만 추가하거나 교체한다.

핵심 연구 대상은 다음과 같다.

- 동적 모듈 구성
- 기능 단위의 실행 및 종료
- 실행 중 구조 변경
- 의존성 관리
- 상태 이전
- 모듈 간 통신
- 증분 업데이트
- 실행 환경 격리

특히 실행 중인 프로그램의 구조를 변경할 때 기존 작업 상태가 손실되지 않도록 하는 것이 중요하다.

## 6.4 Persistent Workspace Engine

Workspace의 생명주기와 상태를 관리하는 자체 런타임이다.

주요 역할은 다음과 같다.

- Workspace 생성 및 종료
- 기능 및 엔진 관리
- 실행 상태 추적
- 상태 저장
- 체크포인트 관리
- 변경 이력 관리
- 복구 및 복제
- 변경 사항 적용
- 실행 중인 구성 요소 관리

Workspace는 단순한 UI가 아니라 독립적인 작업 실행 환경으로 취급한다.

# 7. 추가적인 핵심 기술

## 7.1 Software Capability Model

OS가 소프트웨어를 이해하고 조합하기 위해서는 각 소프트웨어가 제공하는 기능을 표준화된 형태로 표현할 필요가 있다.

이를 위해 Software Manifest와 Capability Model을 설계한다.

Capability는 하나의 실행 가능한 기능 단위다.

예를 들어 데이터 분석 프로그램은 다음과 같은 Capability를 제공할 수 있다.

- CSV Reader
- Data Filter
- Statistical Analysis
- Correlation Analysis
- Chart Renderer
- Export

각 Capability는 다음 정보를 가질 수 있다.

- 고유 ID
- 기능 설명
- 입력 및 출력 타입
- 의존성
- 실행 조건
- 필요한 권한
- 리소스 요구량
- UI Extension Point
- API 또는 IPC 인터페이스
- 호환성 정보

Software Manifest는 특정 소프트웨어가 제공하는 기능과 사용 조건을 기술한다.

OS는 이를 기반으로 작업에 필요한 기능을 탐색하고 조합한다.

## 7.2 Capability Resolver

사용자의 작업에 필요한 기능을 찾아 구성하는 기술이다.

- 필요한 Capability 탐색
- 기능 간 호환성 검사
- 의존성 해결
- 실행 순서 결정
- 대체 가능한 기능 탐색
- 권한 및 리소스 확인

## 7.3 Adaptive Composition Engine

Adaptive Composition Engine은 프로젝트의 핵심 독자 기술 중 하나다.

Software Registry에 등록된 기능과 새로운 기능을 분석하고, 작업에 적합한 실행 환경을 구성한다.

주요 구성 요소는 다음과 같다.

- Software Registry
- Capability Resolver
- Adaptation Planner
- Workflow Composer
- UI Synthesizer
- Compatibility Checker
- Patch Manager
- State Migration Manager

AI는 Adaptation Plan을 제안할 수 있지만, 실제 적용 여부는 OS가 검증한다.

## 7.4 Transactional Adaptation

Workspace 변경 과정의 안전성을 보장하기 위한 기술이다.

기존 Workspace를 직접 변경하다가 실패하면 데이터 손실이나 실행 불능 상태가 발생할 수 있다.

따라서 변경 사항은 트랜잭션 방식으로 적용한다.

기본 절차는 다음과 같다.

1. Snapshot: 기존 Workspace 상태 보존
2. Plan: 변경 계획 생성
3. Validate: 타입, 의존성, 권한 및 호환성 검사
4. Stage: 기존 환경과 분리된 상태에서 변경 사항 구성
5. Test: 변경된 환경 검증
6. Commit: 성공한 변경 사항 적용
7. Rollback: 실패하면 이전 상태로 복구

이를 통해 Workspace의 안정성을 유지하면서 동적 변경을 지원한다.

## 7.5 UI Synthesizer

작업에 적합한 인터페이스를 생성하고 변경하는 기술이다.

고정된 프로그램 UI를 그대로 사용하는 대신, 현재 Workspace의 기능과 작업 상태를 기반으로 필요한 UI를 구성한다.

- 패널 생성 및 제거
- 도구 배치
- 데이터 뷰어 구성
- 작업별 컨트롤 생성
- 인터페이스 변경
- 사용자 설정 유지

UI는 Workspace의 다른 상태와 구분된 독립적인 버전으로 관리한다.

## 7.6 Intelligent Resource Runtime

CPU, 메모리, GPU 및 프로세스 자원을 관리하는 자체 런타임을 구상한다.

AI가 시스템 자원을 직접 제어하는 구조는 피한다.

AI는 작업 특성이나 예상 자원 요구량을 제공할 수 있지만, 실제 배분은 운영체제의 검증된 자원 관리기가 담당해야 한다.

주요 연구 대상은 다음과 같다.

- CPU 및 메모리 관리
- GPU 작업 배분
- 프로세스 우선순위
- 실행 작업의 자원 요구량 분석
- Workspace별 자원 제한
- 작업 간 자원 충돌 관리
- 실행 성능 모니터링
- 동적 자원 할당

초기에는 Linux의 기존 자원 관리 기능을 활용하되, 상위 계층의 정책과 스케줄링 로직은 독자적으로 연구하고 구현한다.

# 8. 전체 시스템 아키텍처

전체 아키텍처는 여섯 계층으로 구성한다.

## L1. Hardware & Kernel Layer

하드웨어와 운영체제 커널을 담당한다.

초기에는 Linux 커널을 기반으로 개발한다.

주요 역할:

- CPU 및 메모리 관리
- 프로세스 관리
- 파일 시스템
- 네트워크
- 장치 드라이버
- GPU 드라이버
- 기본적인 시스템 호출

장기적으로 자체 커널 개발 가능성을 연구할 수 있지만, 초기 프로젝트의 핵심은 커널을 새로 만드는 것이 아니다.

상위 시스템이 특정 커널에 과도하게 종속되지 않도록 독립적인 시스템 인터페이스를 설계한다.

## L2. System & Security Runtime

운영체제의 기본 실행 환경과 보안 기능을 담당한다.

주요 구성:

- Process Manager
- Service Manager
- IPC
- File Access Manager
- Network Access Manager
- Resource Manager
- Isolation Runtime
- Capability Security System

프로세스와 서비스는 독립적으로 실행되며, Workspace가 이들을 통합적으로 관리한다.

초기 기술 후보:

- Linux namespaces
- seccomp
- cgroups
- Unix Domain Socket

## L3. Intelligence Runtime

사용자의 의도를 이해하고 작업 계획을 생성하는 계층이다.

주요 구성:

- Intent Understanding
- Task Planner
- Model Router
- Context Manager
- Structured Output Generator
- Output Validator
- Local Model Runtime

로컬 sLM을 우선적으로 활용하고, 더 복잡한 작업에는 필요에 따라 더 강력한 로컬 또는 원격 LLM을 사용할 수 있다.

다만 AI는 OS의 권한을 직접 가지지 않는다.

AI는 작업 계획과 AIR을 제안하는 역할을 수행하고, 검증과 실행은 OS가 담당한다.

## L4. Adaptive Composition Engine

프로젝트의 핵심 독자 기술이 위치하는 계층이다.

주요 구성:

- Software Registry
- Software Analyzer
- Semantic Reconstruction
- Capability Resolver
- Adaptation Planner
- AIR
- Adaptive Compiler
- Workflow Composer
- UI Synthesizer
- Patch Manager
- Compatibility Checker
- Transactional Adaptation

소프트웨어를 분석하고 구성하며, 필요한 경우 새로운 기능을 생성하고 기존 환경을 변경한다.

## L5. Workspace Runtime

작업 환경의 실행과 생명주기를 관리한다.

주요 구성:

- Workspace Manager
- State Manager
- Version Manager
- Checkpoint Manager
- Execution Manager
- Module Manager
- Recovery Manager

Workspace의 생성부터 종료까지 모든 상태를 관리한다.

## L6. Unified Experience

사용자가 실제로 상호작용하는 계층이다.

주요 구성:

- Adaptive Desktop
- Workspace Shell
- Dynamic UI
- Interaction Manager
- Notification System
- Task Interface

사용자는 여러 프로그램을 직접 다루는 대신 하나의 Workspace를 이용한다.

# 9. 시스템 내부 데이터 모델

초기 구현에서는 복잡한 일반화보다 최소한의 명확한 데이터 모델을 우선한다.

## 9.1 Workspace

Workspace는 다음과 같은 정보를 가진다.

```rust
struct Workspace {
    id: WorkspaceId,
    goal: TaskGoal,
    version: WorkspaceVersion,
    software: SoftwareConfiguration,
    workflow: WorkflowState,
    interface: InterfaceState,
    data: DataState,
    history: VersionHistory,
}
```

이는 개념적 예시이며 실제 타입과 API는 구현 과정에서 결정한다.

## 9.2 Workspace Plan

Workspace의 구성과 변경을 표현하는 계획이다.

```rust
struct WorkspacePlan {
    base: WorkspaceId,
    capabilities: Vec<CapabilityBinding>,
    workflow: WorkflowGraph,
    interface: InterfaceSpec,
    permissions: CapabilitySet,
    state_migrations: Vec<StateMigration>,
}
```

## 9.3 Capability Binding

```rust
struct CapabilityBinding {
    capability: CapabilityId,
    enabled: bool,
    config: Configuration,
}
```

각 구성 요소의 실제 설정, 의존성, 실행 조건 및 권한은 별도 스키마로 정의한다.

## 9.4 Software Manifest

Software Manifest는 소프트웨어가 제공하는 기능과 OS가 접근할 수 있는 인터페이스를 설명한다.

개념적으로 다음 정보를 포함한다.

- Software ID
- Name 및 Version
- 제공 Capability
- 입력 및 출력 타입
- 의존성
- 권한
- 실행 환경
- 리소스 요구사항
- Extension Point
- UI 정보
- 호환성 및 변경 가능 범위

## 9.5 AIR

AIR은 Workspace 구성과 변경을 표현하는 중간 표현이다.

초기 버전에서는 다음 요소를 우선 지원한다.

- Workspace 선언
- Capability 선언
- 기능 활성화 및 비활성화
- Workflow 연결
- 데이터 흐름
- UI 구성
- 권한 선언
- 상태 이전 선언

이후 실행 중 동적 변경, 고급 최적화, 소프트웨어 분석 결과 등을 추가한다.

# 10. AI와 운영체제의 역할 분리

AI-Native OS에서 가장 중요한 설계 원칙 중 하나는 AI와 운영체제의 책임을 분리하는 것이다.

AI 모델은 확률적인 결과를 생성한다.

따라서 모델이 생성한 결과를 곧바로 실행하거나 커널 권한으로 전달해서는 안 된다.

역할을 다음과 같이 분리한다.

### AI의 역할

- 사용자 의도 이해
- 작업 분해
- 필요한 기능 탐색
- 구성 계획 생성
- AIR 생성
- 코드 생성
- 기능 변경 제안
- 분석 결과 해석

### OS의 역할

- AIR 검증
- 타입 검사
- 의존성 검사
- 권한 검사
- 자원 확인
- 실행 계획 생성
- 샌드박스 실행
- 변경 사항 적용
- 실패 시 롤백
- 상태 보존

즉, AI는 무엇을 해야 하는지 제안하고, OS는 그것을 안전하고 효율적으로 수행할 수 있는지 판단한다.

AI가 만든 기능은 검증과 테스트를 통과하기 전까지 실제 사용자 데이터에 영향을 주어서는 안 된다.

# 11. 성능 중심 설계

Xdaptive는 AI 기능만을 강조하는 운영체제가 아니다.

실제로 사용할 수 있는 수준의 성능과 안정성을 확보하는 것을 중요한 목표로 삼는다.

AI 호출이 모든 작업의 실행 경로에 들어가면 지연 시간이 증가하고 자원 낭비가 발생한다.

따라서 다음 원칙을 적용한다.

## 11.1 AI와 일반 실행 경로 분리

- 일반 작업은 AI 호출 없이 실행한다.
- AI는 작업 이해와 구조 변경이 필요한 시점에만 호출한다.
- 생성된 실행 계획은 검증 후 재사용한다.
- 반복 작업은 매번 새롭게 계획하지 않는다.

## 11.2 증분 변경

Workspace 전체를 매번 새로 구성하지 않는다.

변경된 부분만 분석하고 재구성한다.

- 증분 컴파일
- 의존성 캐싱
- 변경 범위 분석
- 부분적인 UI 재구성
- 실행 모듈 재사용

## 11.3 데이터 처리 최적화

- 불필요한 데이터 복사 최소화
- 불변 객체 및 참조 활용
- 변경 로그 활용
- 체크포인트 관리
- 메모리 사용량 추적
- 필요에 따른 병렬 처리

## 11.4 네이티브 실행

컴파일된 실행 계획은 가능한 한 네이티브 실행 환경에서 처리한다.

모든 작업을 인터프리터나 AI 에이전트에 의존하지 않는다.

## 11.5 자원 관리

- CPU 및 메모리 사용량 제한
- GPU 작업 관리
- Workspace별 자원 격리
- 작업 우선순위 관리
- 예측 가능한 실행 정책

성능은 단순히 빠르다는 주장으로 증명하지 않는다.

실제 측정과 비교를 통해 검증한다.

# 12. 보안 및 안정성

동적으로 프로그램을 생성하고 변경하는 운영체제에서는 보안과 안정성이 특히 중요하다.

## 12.1 권한 기반 실행

AI가 생성한 프로그램이 사용자 시스템 전체에 접근할 수 있어서는 안 된다.

각 Capability와 Workspace에 필요한 권한만 부여한다.

## 12.2 격리

실행 모듈은 서로 격리된 환경에서 동작할 수 있어야 한다.

초기에는 Linux의 namespaces, seccomp, cgroups 등을 활용한다.

## 12.3 검증된 변경

모든 변경은 다음 절차를 거친다.

- 구조 검증
- 타입 검사
- 의존성 검사
- 권한 검사
- 리소스 검사
- 테스트 실행
- 적용 또는 롤백

## 12.4 상태 복구

Workspace 변경 중 오류가 발생하면 이전의 정상 상태로 돌아갈 수 있어야 한다.

이를 위해 스냅샷, 체크포인트, 변경 로그 및 상태 이전 메커니즘을 설계한다.

## 12.5 저장 및 복구 전략

모든 데이터를 매번 복사하는 방식은 비효율적이다.

다음 기술을 조합하는 방안을 검토한다.

- 불변 객체
- Content-addressed Storage
- 변경 로그
- 증분 스냅샷
- 체크포인트

# 15. 개발 로드맵

프로젝트는 처음부터 완전한 독립 운영체제를 만드는 방식으로 진행하지 않는다.

핵심 기술을 단계별로 구현하고 검증한 후 시스템을 확장한다.

## Stage 0. System Specification

목표: 프로젝트의 기본 개념과 실행 모델을 확정한다.

주요 작업:

- 전체 아키텍처 정의
- 소프트웨어 모델 설계
- Workspace 데이터 모델 설계
- Capability Model 설계
- Software Manifest 설계
- AIR 초기 규격 설계
- 보안 및 권한 모델 설계
- 변경 및 복구 모델 설계

산출물:

- Architecture Specification
- AIR Specification
- Software Manifest Specification
- Workspace Specification
- Security Model
- RFC 문서

## Stage 1. Adaptive Runtime

목표: AI 없이도 선언적인 구성으로 Workspace를 생성하고 변경할 수 있는 런타임을 구현한다.

주요 작업:

- AIR Parser
- AIR Validator
- Software Registry
- Capability Resolver
- Workspace Runtime
- 기본 Workflow Engine
- Linux System Adapter
- 기본 상태 저장 및 복구

가장 중요한 목표는 AI가 없어도 우리가 설계한 소프트웨어 모델이 실제로 동작한다는 것을 증명하는 것이다.

## Stage 2. Software Adaptation

목표: 기존 Workspace를 유지하면서 기능과 구조를 변경하는 기술을 구현한다.

주요 작업:

- Software Adapter
- Capability Composition
- Workflow Composition
- UI Adaptation
- Transactional Adaptation
- State Migration
- Workspace Versioning
- 변경 검증 및 롤백

목표: AIR을 효율적으로 분석하고 실행 가능한 구조로 변환하는 자체 컴파일러를 구축한다.

주요 작업:

- AST 및 Typed IR
- 정적 타입 검사
- 의미 분석
- 의존성 분석
- 실행 계획 생성
- 최적화
- 증분 컴파일
- 실행 모듈 생성

## Stage 4. Intelligence Integration

목표: AI를 이용해 사용자의 의도를 Workspace 구성으로 변환한다.

주요 작업:

- Local sLM Runtime
- Intent Understanding
- Task Planning
- AIR Generation
- Context Management
- Model Routing
- Structured Output Validation

이 단계에서도 AI의 출력은 반드시 검증 과정을 거친다.

## Stage 5. Unified Desktop

목표: 일반 사용자가 실제로 사용할 수 있는 통합 인터페이스를 구축한다.

주요 작업:

- Workspace Shell
- Adaptive Desktop
- Dynamic UI
- 작업 상태 표시
- 기능 변경 인터페이스
- 저장 및 복구
- 사용자 설정

## Stage 6. Independent OS

목표: 완성된 시스템을 독립적인 운영체제 환경으로 발전시킨다.

주요 작업:

- 설치 이미지
- 부팅 및 시스템 서비스
- 패키징
- 업데이트
- 하드웨어 호환성
- 시스템 복구
- 장기적인 자체 커널 연구 및 이전 가능성 검토

# 16. 첫 번째 Proof of Concept

첫 번째 PoC는 지나치게 큰 작업을 선택하지 않는다.

핵심 가설을 검증할 수 있는 데이터 분석 환경을 대상으로 한다.

## 16.1 목표

사용자가 CSV 파일을 분석하고 그래프를 생성하는 작업 환경을 만들도록 요청한다.

이후 새로운 분석 기능을 추가해도 기존 작업 상태가 유지되는지 확인한다.

## 16.2 초기 Workspace

처음에는 다음 기능만 제공한다.

- CSV Reader
- Data Viewer

Chart Engine은 처음부터 설치하거나 활성화하지 않는다.

## 16.3 사용자 요청

사용자가 다음과 같이 요청한다.

"이 데이터의 상관관계를 분석하고 산점도를 추가해 줘."

## 16.4 Adaptive Composition

OS는 기존 Workspace를 분석하고 필요한 변경 사항을 계산한다.

- 기존 CSV Reader 유지
- Data Analysis Capability 추가
- Chart Engine 연결
- Correlation Workflow 구성
- 산점도 UI 패널 추가
- 기존 데이터 및 상태 보존

## 16.5 Workspace v2

변경이 성공하면 새로운 Workspace 버전으로 전환한다.

사용자는 기존 작업 환경을 계속 사용하면서 새롭게 추가된 기능을 이용할 수 있다.

## 16.6 핵심 검증 가설

> 기존 소프트웨어의 기능과 작업 상태를 보존하면서, 작업의 변화에 따라 실행 환경 자체를 안전하게 재구성할 수 있는가?

이 PoC는 AI 기능을 반드시 포함할 필요가 없다.

먼저 AIR과 Workspace Runtime이 실제로 동작하는지 확인한 뒤 AI를 연결한다.

# 17. 연구 과제 및 성능 검증

Xdaptive는 단순히 새로운 인터페이스를 구현하는 개발 프로젝트에 머물러서는 안 된다.

독자적인 기술의 효과를 측정하고 검증할 수 있어야 한다.

## 17.1 소프트웨어 이해 정확도

분석 대상 소프트웨어의 기능을 얼마나 정확하게 추론하는지 측정한다.

평가 요소:

- 기능 식별 정확도
- 입력 및 출력 추론 정확도
- 의존성 분석 정확도
- 동작 재현 성공률
- 호환성 예측 정확도

## 17.2 Capability Composition

여러 기능을 조합할 때 얼마나 정확하고 효율적인지 측정한다.

평가 요소:

- 구성 성공률
- 의존성 해결 정확도
- 구성 시간
- 불필요한 기능 포함 비율
- 실행 실패율

## 17.3 Adaptive Compiler

컴파일러의 성능과 정확성을 검증한다.

평가 요소:

- 컴파일 시간
- 증분 컴파일 시간
- 실행 성능
- 메모리 사용량
- 최적화 전후 성능
- 타입 및 의미 오류 탐지율

## 17.4 Transactional Adaptation

Workspace 변경의 안정성을 측정한다.

평가 요소:

- 변경 성공률
- 롤백 성공률
- 상태 보존 정확도
- 변경 적용 시간
- 실패 시 데이터 손실 여부
- 복구 시간

## 17.5 Runtime Performance

일반적인 작업 실행에서 기존 접근과 비교한다.

평가 요소:

- 실행 지연 시간
- CPU 사용량
- 메모리 사용량
- GPU 사용량
- 프로세스 생성 및 종료 비용
- IPC 오버헤드

## 17.6 AI 효율성

AI가 OS의 구성 과정에서 얼마나 효율적으로 활용되는지 평가한다.

평가 요소:

- Intent 해석 정확도
- AIR 생성 정확도
- 잘못된 계획의 검증 및 차단 비율
- AI 호출 횟수
- 토큰 사용량
- 전체 작업 완료 시간

AI를 사용하지 않는 일반 실행 경로가 얼마나 효율적인지도 함께 측정한다.

# 18. 핵심 설계 원칙

Xdaptive 전체에서 다음 원칙을 유지한다.

### 1. Task-Centric

프로그램이 아니라 사용자의 작업을 중심으로 시스템을 구성한다.

### 2. Adaptive Software

소프트웨어를 고정된 완제품이 아니라 작업에 따라 구성하고 변경할 수 있는 대상으로 취급한다.

### 3. Unified Experience

내부적으로 여러 엔진과 서비스가 동작하더라도 사용자는 하나의 통합 Workspace를 이용한다.

### 4. Native Performance

일반적인 작업은 AI 호출 없이 효율적으로 실행되어야 한다.

### 5. Incremental Adaptation

전체 환경을 반복해서 재생성하지 않고 필요한 부분만 변경한다.

### 6. Safe Execution

AI가 생성한 계획과 코드를 직접 신뢰하지 않는다. OS가 검증하고 통제한다.

### 7. Persistent State

작업 환경의 상태와 변경 이력을 보존하고 복구할 수 있어야 한다.

### 8. Kernel Independence

초기에는 Linux를 활용하되 핵심 실행 모델과 상위 기술은 독립적으로 설계한다.

### 9. Original Technology

외부 기술을 단순히 조합하는 데 머물지 않고 자체 IR, 컴파일러, 런타임, 자원 관리 및 구성 기술을 개발한다.

### 10. Measurable Engineering

모든 핵심 기술은 실제 구현과 측정을 통해 검증한다.

# 19. 기술적 차별성과 프로젝트의 정체성

Xdaptive의 핵심은 AI가 프로그램을 만들어 준다는 사실 자체가 아니다.

이미 AI 코딩 도구와 에이전트는 코드를 생성하고 기존 소프트웨어를 자동화할 수 있다.

우리의 차별점은 이러한 작업을 운영체제 차원에서 통합하고, 소프트웨어의 표현과 실행 모델 자체를 새롭게 설계한다는 데 있다.

기존 운영체제에서는 프로그램이 먼저 존재하고 운영체제는 그 프로그램을 실행하는 역할을 담당한다.

Xdaptive에서는 작업을 중심으로 운영체제가 소프트웨어의 구성과 실행을 관리한다.

이를 위해 자체적인 중간 표현, 컴파일러, 실행 모델, Workspace Runtime, Capability Model 및 적응형 구성 엔진을 구축한다.

리버스 엔지니어링과 외부 소프트웨어는 활용 가능한 기술적 자원이지만, 프로젝트의 근본적인 차별점은 아니다.

외부 기술을 활용하더라도 핵심적인 소프트웨어 모델과 실행 체계는 우리 스스로 설계하고 구현하는 것이 목표다.

## 19.1 브랜드와 기술 철학의 연결

Xdaptive의 브랜드 정체성은 프로젝트의 기술적 목표와 분리되지 않는다.

**Beyond Applications.**

기존 애플리케이션 중심 컴퓨팅 모델을 넘어선다.

**Software that adapts to your intent.**

소프트웨어는 사용자의 의도와 작업에 맞춰 구성되고 변화한다.

**Adaptation is a system capability.**

적응은 개별 프로그램의 부가 기능이 아니라 운영체제 자체가 제공하는 능력이다.

이 문장들은 프로젝트를 소개하는 표현인 동시에 기술 설계의 방향을 유지하기 위한 기준이다.

Xdaptive는 단순히 AI를 활용하는 운영체제가 아니라, 소프트웨어의 구성과 실행, 변화 및 생명주기를 시스템 차원에서 다루는 새로운 컴퓨팅 플랫폼을 지향한다.

# 20. 최종 비전

궁극적으로 Xdaptive OS가 지향하는 환경에서는 사용자가 프로그램을 찾아 설치하고 사용법을 익히는 과정이 최소화된다.

사용자는 자신이 수행하려는 작업을 설명한다.

운영체제는 작업을 이해하고 필요한 소프트웨어를 구성한다.

기존 기능을 활용하고, 새로운 기능을 생성하며, 실행 환경을 최적화한다.

사용자는 하나의 Workspace 안에서 작업을 수행한다.

새로운 요구사항이 발생하면 소프트웨어는 기존 상태를 유지하면서 변화한다.

이러한 환경에서 소프트웨어는 더 이상 고정된 형태의 제품이 아니다.

소프트웨어는 사용자의 목적을 실현하기 위해 구성되고, 실행되고, 변화하는 시스템의 일부가 된다.

**우리가 만들고자 하는 것은 AI가 프로그램을 대신 조작하는 운영체제가 아니다.**

**소프트웨어가 사용자의 의도에 맞춰 스스로 구성되고 진화할 수 있도록, 그 생성과 실행을 운영체제 차원에서 관리하는 새로운 컴퓨팅 플랫폼이다.**

> **Xdaptive OS**
>
> **Adaptive Computing OS**
>
> **Beyond Applications.**
>
> **Software that adapts to your intent.**
>
> **Adaptation is a system capability.**

# 부록 C. 2026-11-25 확정 사항

부록 B의 질문과 A-2의 미확정 항목 중 다음을 확정했다. 영어 명세(`docs/`)에
반영했고, 번호는 [16-open-questions.md](16-open-questions.md)의 영구 식별자다.

- **구성 최소 단위(#64): Capability.** Module은 구현 그룹, Component는 배포 그룹.
- **AIR Stage 0 범위(#65): PoC에 필요한 표현만.** 이후 RFC로 확장.
- **실행 모듈(#20, #21): 하이브리드(네이티브 + 자체 바이트코드).** 단, 구분은
  코드의 출처가 아니라 정적 분석·검증 수준·실행 권한으로 결정한다. 바이트코드도
  자동으로 안전하지 않으며, 메모리·시스템 호출·자원 사용과 VM 취약점을 검증한다.
  검증된 Capability를 네이티브로 재컴파일하는 것은 미래 확장 방향으로 둔다.
- **모듈 ABI(#22): 최소 골격 + 버전 필드.** 값 전달·오류·비동기 1규칙을 확정하고
  나머지는 RFC로 미룬다. 버전만으로 호환되지 않으며, 실행 전 호환성 검사를 한다.
- **상태 유지(#66): 3단계 정책.** ① State Migration → ② State Re-derivation →
  ③ Reject Change. 모든 Capability에 같은 방식을 강제하지 않는다.
- **원자적 전환(#67):** 새 상태가 검증될 때까지 기존 상태를 보존하고, 실패하면
  기존 상태로 복구하며, 이전 중 데이터 변경이 중복 적용되지 않게 한다. 외부
  시스템·되돌릴 수 없는 작업은 별도 정책이 필요하며, 원자적으로 만들 수 없으면
  변경을 거부한다.
- **PoC 자체 엔진(docs/13):** CSV(따옴표·쉼표·줄바꿈 지원) + 통계(평균·분산·
  상관계수) + 산점도 데이터 + 상태(처리 위치·누적 통계) + 변경(이전·복구).
  데이터 엔진과 OS의 인터페이스는 이후 Polars/Arrow 같은 외부 엔진을 연결할 수
  있게 설계한다. 핵심 실험은 **실행 중 데이터 처리 Capability를 교체하고 결과의
  일관성과 상태 보존을 확인하는 것**이며, 검증은 수치 허용 오차와 상태 무결성의
  두 계층을 모두 통과해야 한다(RFC 0002).
- **AI 전략(#39, #45): 로컬 sLM 우선, 원격은 선택적 확장.** 오프라인 동작,
  민감 데이터 외부 전송 금지, 권한·정책에 따른 원격 사용, 원격 불가 시에도
  시스템은 멈추지 않음, AI 출력은 별도 검증 계층 통과, 모델 선택에 메모리·GPU·
  전력 반영.
- **UI(#50, #52): Slint + 프레임워크 독립 UI Composition Layer.** AIR이 패널과
  Capability 관계를 선언하고, Composition Layer가 표시를 관리하며, Slint가
  렌더링한다. egui는 개발자용 디버깅 UI로 허용.
- **리버스 엔지니어링(#46): 별도 연구 저장소로 분리.** 메인 OS는 Stage 0~2의
  핵심 아키텍처 검증에 집중하고, Stage 1~2 이후 통합을 평가한다. 분석 결과를
  신뢰된 선언으로 바로 취급하지 않는다.
- **커널(#59): Linux 유지, 자체 커널 가능성은 열어 둔다.**

## 안전 우선 원칙

> 변경할 수 있을 때만 변경한다. 성능과 적응성을 위해 데이터 무결성을 희생하지
> 않는다.

Xdaptive는 무조건 변경할 수 있는 OS가 아니라, 안전하게 변경할 수 있을 때만
변경하는 OS다. 이는 설계 원칙 6(안전한 실행)과 7(상태 보존)을 하나로 묶은
규칙이다.

- AIR은 **선언적 DSL**, 자체 타입 시스템 + 기본 타입(숫자·문자열·테이블·텐서),
  **명목적 타이핑** 기본, 데이터 전달은 값·참조·스트리밍(GB급 복사 금지),
  명시적 스키마 버전과 마이그레이션, 권한·자원 선언(집행은 런타임).
- **자체 최소 바이트코드 VM**(검증기 + 제한 명령어), **자체 Module ABI**
  (네이티브·바이트코드 모두 지원, C ABI를 내부 표준으로 삼지 않음).
- 격리는 **프로세스 경계 기본**, 신뢰할 수 없는 모델 생성 코드는 VM 샌드박스.
- 저장은 **SQLite + content-addressed storage**.
- 권한은 Capability 단위 최소 권한, 파일(읽기·쓰기·생성·삭제·디렉터리)과
  네트워크(목적지·방향)까지 세분화. 비밀은 Capability에 저장하지 않고 런타임이
  참조·권한만 전달. **감사 로그**로 실행 재구성 가능. 프롬프트·개인정보는 기록
  금지. **AI 없는 경로 우선**.
- **DCO**, 모노레포, 영어 스펙+한국어 마스터, 0.1.0→1.0(SemVer, 초기 호환 제한).
- 첫 공개 마일스톤은 **PoC 성공**(Capability 생성→실행→상태 이전→결과 검증).

## 5대 아키텍처 원칙

1. **기능과 구현을 분리한다.** Capability=기능의 정체성, Module·Component=구현·배포.
2. **선언과 실행을 분리한다.** AIR=구조, Runtime=실행. AIR은 실행 로직을 담지 않는다.
3. **성능과 안전성을 함께 추구한다.** 네이티브·바이트코드를 분석과 신뢰로 선택.
4. **변경보다 무결성이 우선이다.** 안전하게 이전할 수 없으면 변경하지 않는다.
5. **AI는 통제 대상이자 보조 수단이다.** AI는 권한을 갖지 않고, OS가 검증·적용한다.

## 핵심 연구 가설

> 기존 소프트웨어의 실행 구조를 선언적으로 표현하고, 이를 서로 다른 실행
> 모듈로 컴파일하며, 실행 중에도 상태와 무결성을 유지하면서 안전하게 재구성할
> 수 있는가?

가장 큰 위험은 기술을 구현하지 못하는 것이 아니라, 너무 많은 기술을 한꺼번에
시도하다 정작 이 핵심 가설을 검증하지 못하는 것이다.

# 부록 E. 2026-11-25 추가 확정 (언어·용어·상태·배포)

- **구현 언어 중립(#70).** Capability의 정체성은 구현 언어와 독립이다. Module은
  Module ABI만 지키면 어떤 언어로도(Rust, 자체 바이트코드, Xz 등) 구현된다.
  어떤 언어도 핵심 아키텍처의 필수 의존성이 아니다. Xz는 독립 어댑터로 연결하고,
  `.xzint`는 어댑터를 통해 재사용할 수 있으나 Manifest로 직접 채택하지 않는다.
  Stage 0은 자체 바이트코드 경로 하나로 이 구조를 검증한다.
- **Capability와 Permission의 분리(#71).** Capability는 기능 단위, Permission은
  자원 접근 권한이다. Capability 선언만으로 Permission이 부여되지 않는다.
  Runtime이 Permission을 검사·통제하고, Capability별 최소 권한을 적용한다.
  (OS 보안의 capability 용어와의 충돌은 이 구분으로 해소한다.)
- **AIR 제어 흐름(#72).** 선언적 연결과 **경계가 있는 조건부 게이트(if/when)**만
  허용하고, **일반 반복은 표현하지 않는다.** 조건은 임의 코드가 아니라 타입·구조가
  명확한 조건이다. 반복은 Capability 구현이나 스트리밍 엔진에 위임한다.
- **차원·단위 타입(#73).** Stage 0에서는 도입하지 않고 별도 RFC로 연구한다.
  기본·구조 타입만 쓰되, 타입 시스템은 차원 검사를 나중에 추가할 수 있게 확장
  가능하게 유지한다.
- **상태 소유권(#74).** Runtime이 Capability 상태의 생명주기를 소유한다.
  Capability는 버전이 있는 `get_state`/`set_state` 인터페이스를 노출하고, Runtime은
  상태의 내부 의미까지 이해할 필요는 없다. 상태 스냅샷에는 식별자·스키마 버전·
  데이터·무결성 정보가 포함된다. GPU·DB·소켓 같은 외부 자원은 관리 핸들로 다루고
  명시적 복구 정책을 둔다.
- **AI의 레지스트리 접근(#75).** 모델은 Runtime이 관리하는 레지스트리에 **구조화
  조회(tool calling)**로 접근한다. RAG는 선택적 발견 보조일 뿐 실행 권한의 근거가
  아니다. 발견·선택·검증·승인·실행은 분리한다. Capability 메타데이터는 지시로
  취급하지 않는다(프롬프트 인젝션 방지).
- **배포(#76).** `aos`는 crates.io + GitHub Releases, Capability는 GitHub Releases의
  독립 패키지, 로컬 Capability Registry, 구현 언어 독립 Manifest. 설치 무결성과
  실행 권한 검증은 분리한다. 자체 패키지 매니저·원격 레지스트리·서명·시스템
  패키지는 후속.
- **생성 코드 라이선스(#77).** Xdaptive 자체는 Apache-2.0, **생성 코드는 프로젝트
  라이선스를 자동 승계하지 않는다.** 생성물 라이선스는 사용자가 지정하며, 외부
  코드·모델 약관은 별도로 준수한다. (GENERATED-CODE-POLICY.md)

## 용어 원칙

문서·RFC·코드·API에서 **Capability(기능 단위)와 Permission(권한)**을 같은 의미로
쓰지 않는다. 이 구분은 docs/00-glossary.md의 "Terminology and security"에
명시한다.

# 부록 F. 2026-11-26 확정 (ABI·VM·타입·스왑·결정성·환경·관측)

전체 결정은 [docs/17-adr.md](17-adr.md)에 통합했고, 원장 번호는 #78~#84다.

- **ABI 메모리(#78).** 작은 값은 정규 ABI로 값 전달, 큰 데이터는 Runtime 관리
  **핸들**로 전달. 핸들은 주소가 아니라 리소스 식별자이며 소유자·수명이 정의된다.
  핸들이 곧 zero-copy는 아니다.
- **VM(#79).** **스택 머신 + 필수 정적 검증.** 검증 실패한 바이트코드는 실행 전
  거부. 무한 루프·메모리는 별도 자원 제한으로 다룬다.
- **AIR 타입(#80).** **Nullable(`Option<T>`)과 Missing(필드 존재)**을 분리하고
  **명시적 네임스페이스**(`core::Int`, `csv::Row`)를 도입. 차원 타입은 후속 RFC.
- **비동기 스왑(#81).** **Graceful Drain 우선 + 제한적 취소.** Running → Draining
  → Stopped, 하드 타임아웃, 취소·복구가 안전하지 않으면 스왑 거부.
- **결정성(#82).** **3단계 모델** — 비트 단위(정수·직렬화) / 수치(허용 오차) /
  최선 노력(GPU·병렬, 조건 기록). Capability가 선언하고 Runtime이 검증한다.
- **개발 환경(#83).** **Linux 우선 + WSL2 개발 허용.** 격리·프로세스 테스트는 실제
  Linux(CI)에서. Stage 0은 Linux 위 사용자 공간 프로토타입.
- **관측·테스트(#84).** **구조화 이벤트 추적**(스왑별 trace id) + **계층별 테스트**
  (unit / integration / golden / property / failure·swap).

## 추가 원칙

- **최적화보다 의미론을 먼저.** zero-copy·GPU 공유·JIT·네이티브 승격은 데이터
  소유권과 결과 의미가 확정된 뒤에 한다.
- **Runtime은 거부할 수 있다.** 상태 이전 불가·권한 부족·호환 불가는 실행을
  거부하는 것이 올바른 동작이다.
- **Stage 0의 성공 기준은 기능 수가 아니다.** 선언→연결→실행→교체→상태 검증→
  실패 복구의 최소 경로가 작동하는지가 기준이다.

# 부록 G. 2026-11-26 2차 반박 해결 (18건)

부록 F의 결정에 대해 제기한 18개 반박·질문을 직접 해결해 명세에 반영했다.
상세 근거는 `Xdaptive-process/discussions/2026-11-26-design-round-3.md`.

- **핸들 수명(#78).** 세대(generation) 기반 핸들 `(workspace_epoch, slot,
  generation)` + 단일 소유(move). 무효 핸들은 **조용한 오류가 아니라 감지·거부**.
  refcount·zero-copy는 이 설계 위에 후속.
- **검증기 vs AIR 타입(#79).** **타입 있는 바이트코드** — AIR 타입 id를 바이트코드에
  실어 검증기가 같은 패스에서 구조·타입을 함께 검사. "검증 통과 = AIR 호환".
- **Presence(#80).** `Presence<T>` 값 타입 폐기. `Option<T>`는 값 타입, 필드 부재는
  **레코드 수준 presence 플래그**(`name?: T`). 기본 타입은 전역, 사용자 타입만 네임스페이스.
  `Option`은 내장 생성자(사용자 제네릭 아님).
- **취소 불가 악용(#81).** 드레인 **하드 상한**은 Workspace 정책, 초과 시 **스왑 거부**
  (상태 보존). 강제 종료는 `disposable` 선언 Capability에만.
- **결정성 검증(#82).** 검증 단계에서 run-twice 확인 → **서명된 검증 기록**에 저장,
  런타임은 기록을 신뢰. 수준은 **출력 단위**로 선언.
- **외부 부작용 스왑(#81).** 비지원이 아니라 **idempotent 또는 compensable 선언** 시
  지원. PoC는 부작용 없는 경우만 검증.
- **trace 전파(#84).** 모든 호출이 **trace context**(trace id + span id)를 ABI로 전달.
- **버전 4개(#85).** AIR 스키마·ABI·Capability·상태 스키마를 하나의 **호환성 매트릭스**로.
- **디스어셈블리(#79).** VM 스펙에 **정규 디스어셈블리** 포함(골든 테스트 안정성).
- **검증기 신뢰(#36, #79).** 소규모 명령어 집합 + 퍼징/속성 테스트로 위험 완화,
  검증기 **형식 검증은 Stage 3** 로드맵.
- **자원 제한(#79).** instruction budget + wall-clock timeout + 메모리 상한.
- **로그(#84).** 타입 있는 이벤트 스키마 + 교체 가능 인코딩(JSON → binary).
- **ADR/RFC/원장(#13).** 세 기록은 입도가 달라 유지(상태/서사/제안).
- **`Xdaptive-process/`(#17).** 공개 저장소에 **커밋**(설계 과정의 공개 원칙).
- **개발 환경(#83).** WSL2 확인(`6.18.33.2-microsoft-standard-WSL2`, cgroup v2).
  격리 검증은 실제 Linux CI 기준.

## 반성

"move만"·"부작용 스왑 비지원"·"결정성 선언 신뢰"는 지나치게 보수적이었다. 세대 핸들,
idempotent/compensable 선언, 서명된 검증 기록이 더 정확하고 더 야심차다. 다음 단계로
과도하게 미루지 않는다.
